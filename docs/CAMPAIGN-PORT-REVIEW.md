# Fallout 2 — Campaign Port Review

> Grounded scoping of porting the **full** FO2 campaign to Hexwaste. Produced by a 12-agent
> review workflow (2026-06-30) grounded against the Hexwaste code, `reference/fallout2-ce`, and
> the user's own game data via `--smoke` / `ProcAnalyze` / `DatDump`. "Porting the campaign"
> means **wiring the engine so the original scripts (already in the user's data) run to**
> **completion** — no game content is reproduced or embedded.

## Executive summary

Hexwaste already runs the FO2 campaign as a substrate: all 155 maps load/walk, dialog/combat/worldmap/timers/party/GVARs/Pip-Boy quest-log all work, and 126 of 181 externals are genuinely wired. "Porting the campaign" therefore does NOT mean building systems — it means (a) wiring a small, bounded batch of stubbed EFFECT/climax externals so the original scripts can drive their GVARs to completion thresholds, (b) building the one truly-missing subsystem that gives the game a conclusion (the endgame slideshow/movie + the karma/rep effects that select the slides), and (c) the dominant cost: per-quest playtest/QA across ~150 quests, because completion today is only ever reached by actually playing each dialog/combat/item chain (there is no automated end-to-end driver, and --smoke only exercises map_enter/map_update so it under-reports the real stub demand). The engine delta is a few weeks; the validation is months. Net: the leverage is overwhelmingly in a handful of shared externals plus the endings — fix those and most of the game becomes completable region by region. This is finishing the game, not adding a feature.

**Total effort:** XL — this is finishing the game, not shipping a feature. The ENGINE delta is small and bounded: the shared externals pass ~M, dialogue_system_enter ~S-M, load_map ~S-M, the map_update/global-init fix ~S-M, the endgame slideshow + karma-effects ~L, the prizefight orchestrator ~M-L, and the optional car/heads/speech ~L each. Call the engine work a few focused weeks. But the DOMINANT cost is per-quest playtest/QA validation across ~150 quests in ~155 maps with no automated end-to-end driver and a smoke harness that only exercises map_enter/map_update — that is the XL, realistically multi-month. Order of magnitude: weeks of engine code + months of content QA for a faithful end-to-end campaign. Critically, almost none of it is new subsystems — ~85-90% of the campaign is already 'machinery-wired-content-gated', so the magnitude is in connecting and then proving, not building.

**Bottom line:** Hexwaste is far closer to a complete FO2 than 'no quest completes on its own' suggests: the expensive engine (dialog VM, GVAR store + Pip-Boy quest log, party/companions, full combat with death procs, live timers, caps/barter, worldmap travel) is built and golden-tested, and ~85-90% of the campaign is content-gated rather than engine-blocked. The leverage is a short, shared list — wire the ~15 stubbed EFFECT externals (dialogue_system_enter and load_map first, they alone unblock terminals across five regions and the entire late-game tanker spine), build the endgame slideshow + karma-effects that select it, and add the map_update/global-init reliability fix — and most of the game becomes completable. No mod-engine/sfall layer is needed for the vanilla campaign; that is settled and only matters if scope ever shifts to RPU/Restoration/total conversions. The honest gating reality is QA, not code: completion is reached only by actually playing each chain, so after a few weeks of engine wiring the real project is months of region-by-region playtest validation. Start with the shared externals pass and the endings — that is where one unit of work unblocks the most quests.

## Mod engines (sfall / Restoration Project) — verdict

**Vanilla campaign needs a mod engine: NO.**

No — porting the VANILLA Fallout 2 campaign does NOT require thinking about a mod engine. Three independent groundings agree: (1) ENGINE: fallout2-ce already bundles sfall's scripting layer (interpreter_extra.cc:5056 sfallOpcodesInit, sfall_opcodes.cc:1040+) but the vanilla campaign never calls into it — the last vanilla opcode is 0x8155 (interpreter_extra.cc:5054). (2) HEXWASTE: it ported exactly that vanilla subset — ExternalArity.cs:19-200 ends at 0x8155, and IntVm.cs:1686-1689 hard-throws on any higher (sfall) opcode; the fact that all 155 maps load/walk/run map_enter+dialog with no 'Unknown external opcode' throw proves the vanilla subset is sufficient. (3) DATA: a full scan of all 1443 vanilla scripts/*.int in master.dat+patch000.dat finds 0 sfall opcodes; --smoke on artemple/denbus1/newr1 shows the only stubbed externals are vanilla (e.g. use_obj_on_obj 0x8145). game-data/sfall.dat is sfall's OWN hi-res UI art + two optional global scripts (gl_highlighting/gl_partycontrol) — not campaign content — and Hexwaste's VFS already doesn't mount it (GameFileSystem.cs:37). Mods ONLY matter if scope ever shifts to running Restoration Project / RPU / Et Tu / total conversions: those genuinely require an sfall layer (0x8156+ opcodes, hookscripts, global scripts, arrays, ini reading, override-DAT mounting), which is a large, separate, out-of-scope effort. For the campaign in front of us, sfall is already accounted for and nothing further is needed.

**What sfall is.** sfall is the classic Fallout 2 engine extender (ships as ddraw.dll, configured via ddraw.ini). It provides four things: (1) a SCRIPT EXTENDER — ~200 new SSL builtins in the opcode range 0x8156 and up (proto read/write, arrays/lists, ini reading, version queries, world-map control, hookscripts, sfall global vars/scripts) on top of the vanilla 0x80A1-0x8155 set; (2) ENGINE BUG FIXES for the original 1.02 exe; (3) HI-RES / DX9 rendering (in concert with Mash's f2_res patch, also bundled in game-data); (4) HOOKS + configurable gameplay tweaks. CRITICAL: fallout2-ce — the codebase Hexwaste ports from — already bakes sfall's scripting layer in. interpreter_extra.cc:5056 unconditionally calls sfallOpcodesInit() (reference/fallout2-ce/src/sfall_opcodes.cc:1040-1127) right after registering the vanilla opcodes (interpreter_extra.cc:5049-5054, last vanilla = 0x8155 op_critter_stop_attacking), plus sfall_config.cc/sfall_global_scripts.cc/sfall_global_vars.cc/sfall_arrays.cc/sfall_metarules.cc and a large set of sfall-tagged engine fixes. So at the engine level fallout2-ce is effectively 'sfall + fixes + hi-res built in'. Hexwaste, however, only ported the VANILLA subset: ExternalArity.cs:19-200 registers exactly 0x80A1..0x8155 and nothing above; IntVm.cs:1686-1689 THROWS 'Unknown external opcode 0x{op}' for anything not in that table — i.e. any sfall opcode (>=0x8156) would hard-fail rather than silently stub. The hi-res and engine-fix dimensions of sfall are moot for Hexwaste: it renders via its own MonoGame pipeline (not the 640x480 exe) and ports already-fixed logic from fallout2-ce, so it inherits neither the original bugs nor the need for a resolution patch.

**The `sfall.dat` in game-data (grounded).** game-data/sfall.dat is the GOG-bundled sfall payload (397 KB, zlib/DAT2). DatDump (--dat game-data/sfall.dat list) shows it is NOT vanilla campaign content: it contains sfall's own support assets only — hi-res/extended interface art (art/intrface/appherowin.frm, barter_e.frm, invbox_e.frm, loot_e.frm, trade_e.frm, use_e.frm, iface_apbar_e.frm, mvenum.frm, worldmap.frm), art/tiles/gridmask.frm, a desc.id, and two SFALL GLOBAL SCRIPTS: scripts/gl_highlighting.int and scripts/gl_partycontrol.int (item-highlight toggle and party-orders UI). I scanned every script in-memory (DAT2 footer/tree per Dat2Archive.cs, zlib-decompressed, opcode-disassembled per tools/int_analyze.py): the two gl_*.int DO use sfall opcodes heavily (gl_highlighting 21 distinct >=0x8156 incl. 0x8204/0x8210/0x822f; gl_partycontrol 28 distinct incl. 0x8156/0x81dc/0x822e) — these are loaded only by the sfall engine (ddraw.dll), never invoked by the campaign. By contrast the VANILLA scripts tell the opposite story: across all 1443 scripts/*.int in master.dat+patch000.dat, ZERO use any opcode >=0x8156 (0 parse errors). The project's own --smoke harness corroborates from the runtime side: artemple stubs=0[]; denbus1 (the Den, where the Vic spine runs) stubs=1[use_obj_on_obj (0x8145)] — a VANILLA opcode, not sfall; newr1 stubs=0[]; and no run ever throws 'Unknown external opcode'. Hexwaste also already ignores sfall.dat: GameFileSystem.cs:37 mounts only patch000.dat, critter.dat, master.dat (plus loose data/), so the sfall.dat _e interface FRMs (hi-res variants the vanilla UI never references) and the gl_*.int (which would crash the 0x8155-capped VM) are never seen. Net: Hexwaste does NOT need to handle any sfall opcode for the vanilla campaign.

**Mod projects (only relevant if scope shifts to mods):**

- **killap's Unofficial Patch (RPU / Fallout 2 Restoration Project base patch)** — Hundreds of bug fixes plus restored cut content (dialog, items, minor map/script fixes). Distributed as override DATs/loose files that shadow master.dat. New and edited scripts that lean on sfall builtins and hookscripts. _Requires:_ Requires sfall (ddraw.dll). Engine support Hexwaste lacks: the 0x8156+ sfall opcode handlers, hookscripts (register_hook), sfall global vars (sfallgv.sav), and mounting the patch's override DATs in the VFS. Out of scope (mod engine + content).
- **Restoration Project (killap, full)** — Large content restoration on top of RPU: whole new locations (EPA, Abbey, Primitive Village, Vault 23, expanded Hubologists, etc.), new NPCs/quests, new global scripts and hookscripts, new proto/art. _Requires:_ Requires sfall heavily (global scripts gl_*, hookscripts, arrays, proto read/write opcodes, ini reading). Needs the full sfall opcode set + global-script/hookscript runtime + override-DAT mounting. Out of scope — both a mod engine and content effort, far beyond the vanilla port.
- **Et Tu (Fallout 1 on the Fallout 2 engine)** — Re-implements the entire Fallout 1 campaign as content running on the FO2/sfall engine (FO1 maps, scripts, protos rebuilt for FO2). _Requires:_ Total dependence on sfall (it is an sfall-based conversion). Would need the complete sfall scripting layer plus its own asset set. Out of scope; it is a different game's content riding the same extender.
- **sfall total-conversions / mega-mods (Fallout: Nevada, Olympus 2207, Last Hope, Sonora-style)** — Brand-new games: custom maps, protos, art, and scripts written against sfall's extended API (arrays, hookscripts, custom opcodes, ini-driven config, custom UI). _Requires:_ Require a near-complete sfall implementation: 0x8156+ opcodes (sfall_opcodes.cc), hookscripts, global scripts, sfall arrays (0x820D-0x820F...), get_ini_setting, sfall global vars, and loading their override DAT chain. Out of scope — supporting them is a standalone engine project, not part of the vanilla campaign port.

**Recommendations:**

- Do nothing for the vanilla campaign: the 0x80A1-0x8155 coverage in ExternalArity.cs is complete and proven (0/1443 vanilla scripts use sfall opcodes; smoke shows only vanilla stubs like use_obj_on_obj 0x8145). No sfall/mod layer to add.
- Keep GameFileSystem.cs:37 NOT mounting sfall.dat — that is correct. Its _e-suffixed art/intrface FRMs are hi-res UI variants the vanilla 640x480 interface never references, and its gl_*.int global scripts use opcodes >=0x8156 that would trip the IntVm throw. Add a one-line code/doc comment recording WHY sfall.dat is intentionally skipped, so it isn't 'helpfully' added later.
- Treat the IntVm.cs:1689 'Unknown external opcode' throw as the right guard rail for an accidentally-modded --game-dir (e.g. someone points it at an RP/RPU install). Consider making that message name the cause explicitly (e.g. 'opcode 0x{op} is an sfall/mod extension; only the vanilla 0x80A1-0x8155 set is supported') so it fails loudly and legibly instead of looking like a parser bug.
- Ignore sfall's hi-res and engine-fix dimensions entirely: Hexwaste renders via its own MonoGame pipeline and ports already-fixed logic from fallout2-ce, so neither the f2_res/DX9 hi-res patch nor sfall's exe bug-fixes are relevant.
- If mod support is ever desired, scope it as its own dedicated phase, NOT a tweak to the vanilla port: it means implementing the sfall_opcodes.cc range, hookscripts, sfall global scripts/vars, arrays, get_ini_setting, and override-DAT mounting — a standalone engine effort comparable in size to the existing script VM, and explicitly out of the current vanilla-campaign scope.

## Recommended sequence

1. PHASE 0 — Shared engine externals pass (highest leverage, unblocks quest completions in EVERY region). In one focused sprint wire: dialogue_system_enter (terminals across 5+ regions), load_map + deferred-transition GVAR (the tanker->Oil Rig spine + all city scene-changes), and the EFFECT batch (kill_critter, use_obj_on_obj, attack_setup [route NPC-vs-NPC to StartBrawl], explosion, critter_heal/critter_mod_skill/critter_rm_trait, get_poison, scripts_request_world_map, wm_area_set_pos). Each bridges to a system that already exists. ~M.

2. PHASE 1 — Engine reliability fixes that make played-through chains stick: the recurring map_update 600-tick heartbeat + run-every-scripted-object's global-init at map enter (fixes time-varying quests + the Den gang war exports). ~S-M.

3. PHASE 2 — Build the conclusion: the endgame slideshow + movie subsystem reading endgame.txt/enddeath.txt + ending GVARs (reuse Shell.cs bookend + FRM/sibling-palette loader), plus the karma/reputation EFFECTS that auto-adjust on kills/quests and select the slides. This converts 'all quests reach their GVAR' into 'the game ends' and gives every town-fate choice a payoff. ~L.

4. PHASE 3 — Harden the OPENING as the end-to-end QA golden path (it is already a runnable spine: artemple->arcaves->arvillag->argarden->arbridge->worldmap). Use it to build/validate a dialog-driving QA harness (extend --talk-seq into a proc-walker) since --smoke under-reports.

5. PHASE 4 — Region-by-region playtest/QA in worldmap-reachability order, driving each quest's dialog/combat/item chain to its terminal set_global_var and confirming the Pip-Boy log + ending slides: Klamath+Den -> Modoc+Vault City -> Gecko+Broken Hills -> NCR+Redding+Vault 15 -> San Francisco+Vault 13 (the load_map tanker gate from Phase 0 unlocks this) -> Enclave endgame + Horrigan -> credits. This is the bulk of the calendar time and it is QA, not engine.

6. PHASE 5 — New Reno's one real feature: run combat_is_starting/over_p_proc on combat boundaries + the prizefight ring orchestrator (Boxing Champion). ~M-L.

7. PHASE 6 (optional / authenticity, NOT completion-blocking) — the Highwayman car subsystem (or scope T-Ray to item/GVAR-only to skip it), holodisks, and talking-head FRM animation + ACM speech/subtitles.
